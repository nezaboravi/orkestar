# Agent formats — the map

One source of truth (OpenCode-format markdown in `agents/` and `teams/`) is
installed by `orchestra.mjs`. Codex, Claude Code, Kimi Code, and OpenCode have
independent model routes and credentials.

These files are durable permission envelopes. Lenka creates one-run specialist
roles at dispatch time by combining an outcome charter, one envelope, and one
live adapter-specific model. A file name is not a permanent team member.

## Runtime routing manifest

- Location: `.agent-orchestra/runtime/<harness>.json`
- Generated per project after live installer probes; ignored by Git
- Contains: harness, lifecycle, fail-closed policy, capability profile,
  permission envelope, model class, selected live model, write flags, and
  independent-proof requirement; Codex manifests also contain the selected
  reasoning effort
- Never contains provider credentials, tokens, or copied authentication state
- Lenka reads this file directly and does not repeat model discovery during a
  task

## Run audit

- Location: `.agent-orchestra/runs/latest.json` and one file per OpenCode root session
- Generated by the installed `orchestra-report` tool immediately before Lenka's final answer; ignored by Git
- Contains: truthful `DONE`, `PARTIAL`, or `FAILED` status, every root and child session, actual agent name, actual provider/model, exact OpenCode input/output/reasoning tokens, exact recorded cost, observed Taskavel state, a requirement-to-evidence proof matrix, and blockers
- Uses OpenCode's session database as the source of truth; it never estimates missing telemetry
- Rejects `DONE` development runs without recorded `dev-planner`, `dev-builder`,
  `dev-tester`, and `dev-auditor` sessions. It also requires `product-designer` and `frontend-qa`
  sessions when design or visual proof was declared necessary.
- Solo runs use Solo's process inventory and output instead: phase workers are
  sibling Solo processes, so they are intentionally outside OpenCode's child
  session database.
- Each proof item records an acceptance criterion, independent method, observed
  result, and direct evidence. A command name or green exit status alone is not
  behavior proof.
- Read after the session with `lenka report last`; that command refreshes the saved root and child usage from OpenCode so the final response itself is included
- Other harnesses remain honest: until an adapter has a proven telemetry collector, their per-agent usage is reported as unavailable rather than copied from another provider or shown as zero

OpenCode project plugins are installed under `.opencode/plugins/`. The shipped
state plugin resolves handoff and report locations from the active session's
`context.directory`, because `context.worktree` may be `/` before a new project
has been initialized as a Git repository. Persistence at a filesystem root is
always refused.

## OpenCode

- Location: `~/.config/opencode/agents/*.md` (global), `.opencode/agents/` (project)
- Frontmatter: `description`, `mode` (primary/subagent), `model`, `permission`
  (allow/ask/deny per tool: read, edit, bash, task, skill, ...), `steps`
- Permission model: explicit allowlists, glob patterns, `"*": deny` default

## Claude Code

- Location: `~/.claude/agents/*.md` (global), `.claude/agents/` (project)
- Frontmatter: `name` (required), `description`, `tools` (allowlist), `model`
- Conversion: `permission:` → `tools:` list; Bash rules become `Bash(pattern)`
  where possible; `task` → `Task`; the selected Claude model is written only
  after its live probe succeeds

## Codex CLI

- Location: `~/.codex/agents/*.toml` (personal), `.codex/agents/` (project)
- Keys: `name`, `description`, `developer_instructions` (required), optional
  `model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `skills.config`
- Conversion: `edit: deny` → `sandbox_mode = "read-only"`; otherwise
  `"workspace-write"`; the model slug comes from Codex's own visible catalog
  and is written only after a live probe succeeds; `model_reasoning_effort`
  is generated from the orchestra policy (`low` economy, `medium` mid,
  `high` strongest)

## Kimi Code CLI

- Location: `~/.kimi-code/agents/*.md` (global), `.kimi-code/agents/` (project)
- Frontmatter: `name`, `description`, `tools`, optional `subagents`
- Conversion: the permission envelope becomes a case-sensitive Kimi tool
  allowlist; Lenka embeds `${base_prompt}` so Kimi retains workspace and skill
  instructions; project launch uses `--agent-file` and the verified configured
  Kimi model
- Model routing: without a configured Kimi subagent model pool, every role uses
  the same verified configured model and the manifest reports that limitation
  honestly
- Probe usage: Kimi's text probe does not expose token or cost totals, so the
  doctor reports them as unavailable rather than as zero

## Cursor

- Location: `~/.cursor/agents/*.md` (user), `.cursor/agents/` (project)
- Format: Markdown with `name`, `description`, and `model: inherit`
  frontmatter; rules in `.cursor/rules/*.mdc` with
  `alwaysApply`; skills auto-discovered from `.cursor/skills/`,
  `~/.agents/skills/`, `.claude/skills/`, `.codex/skills/`

## Skills

- Skills are installed into `~/.agents/skills/` as one portable source. A
  client is claimed as supported only after its adapter proves discovery and
  execution from that location. A skill is a folder with `SKILL.md`
  (frontmatter: `name`, `description`; optional `references/` and scripts).
# Repair reproduction gate

Repair packets require both an `accepted-defect` reference and a `reproduction`
reference before dispatch. Reproduction records identify the input, exact output
context or invariant, expected and observed behavior, code revision/diff, and
evidence source. Reviewers must inspect installed framework semantics before
requesting security repairs; hypotheses stay unverified. A complete static proof
is acceptable when it establishes the affected path without assumptions.

The packet validator checks presence and nonblank references, not the truth,
freshness, or authorship of the referenced evidence. Lenka and the independent
auditor must inspect the records; this gate is not a tamper-proof execution sandbox.

## Solo worker result transport

Create one dedicated result scratchpad for each worker attempt, separate from
shared human-readable summaries. The worker writes one JSON object with exactly
`schemaVersion` (1), `runId`, `processId`, `role`, `status` (DONE/PARTIAL/FAILED),
`summary`, `evidence` (string array), and `blockers` (string array). The receipt
contains the scratchpad ID and revision returned by Solo after the write.

OpenCode's `orchestra-solo-result` reads native Solo CLI records and rejects wrong
projects/processes, stale revisions, archived or incomplete artifacts, mixed
Markdown records, invalid envelopes, and DONE without evidence or with blockers.
Reads are bounded to 200 lines, 64 KiB of content and 10 seconds per CLI call.
`SOLO_CLI` may select the installed binary; otherwise use `solo` on PATH, then
macOS system/user application bundles only if the binary is absent. A command
failure never triggers fallback. Failure is explicit.

This is transport validation, not worker authentication or a final approval gate.
The record's role is a claim to compare with native agent session data. Solo actor
metadata is retained without asserting authorship. Evidence content is untrusted;
the reviewer and auditor still inspect it. Other harnesses use complete dedicated
artifact reads manually; automated parity has not been implemented. Shared Solo
MCP write permissions still do not enforce per-artifact ownership.
# Checked Solo dispatch (OpenCode)

`orchestra-solo-dispatch` resolves a profile from the project runtime manifest;
callers cannot supply a different model, role, executable or extra arguments.
A bounded tools-disabled identity turn must match native session role/model
before that session receives its real task in Solo. An authentication failure
stops dispatch. This adds a small real model call, not a free readiness check.

`orchestra-solo-wait` uses a dispatcher receipt owned by the orchestrating
session. It polls native session metadata inside a bounded tool call, rather
than asking the model to poll terminal output. A finished native turn is only
RESULT_READY; independent review, evidence and result validation remain required.
The 15-minute worker deadline returns PARTIAL instead of an unlimited retry.
Receipts are project-local coordination data, not a cryptographic boundary
against another process with write access to the project.

Other harnesses retain their native dispatch paths. The Task Contract and full
workflow are still instruction/schema governed, not a universal enforced state
machine. Do not claim stronger guarantees or untested platform parity.
